# 独立 Replay 协议

这份协议用于让维护者或外部贡献者在不同机器、不同模型工具环境中复现已有 eval case。它补充提交清单和结构化 JSON 结果，目标是让一次 replay 可以被另一位维护者重新检查，而不是把一次手工评分包装成客观基准。

## 最小复现包

每次独立 replay 至少保留以下信息：

1. `case-id` 和被评估的 commit SHA。
2. 运行日期、模型标识、工具版本和操作系统。
3. 脱敏后的原始用户请求，以及足以复现的上下文摘录。
4. 输出中用于判分的最小片段；长日志只保留定位信息。
5. 四个评分维度（正确性、实用性、安全性、简洁性）及每项一条证据。
6. `pass`、`partial` 或 `fail` 结果，以及一个最小后续动作。
7. Markdown 解释和 [`eval-result-template.json`](../examples/eval-result-template.json) 中一致的结构化结果。

缺少模型、工具、commit 或输入信息时，应将结果标记为待复核，不要用推测补齐环境字段。

## 推荐执行步骤

```text
1. 从 docs/eval-case-index.md 选择已有 case-id。
2. 固定 evaluated_commit，并从该 commit 检出 skill 和 case。
3. 记录环境；删除 token、cookie、私有仓库内容和未脱敏日志。
4. 只运行一次目标 case，保存输入、关键输出和不可用工具说明。
5. 按 docs/scoring-rubric.md 独立评分，再查看 scoring-calibration.md。
6. 填写 Markdown 报告和 JSON 结果，核对 case、commit、分数和证据。
7. 运行 python .\scripts\validate.py，并提交最小证据包供维护者复核。
```

## 维护者复核重点

- 输入和输出是否足以让另一位维护者判断结果。
- 评估的 commit 是否真实存在，且没有把未发布工作混入结果。
- 分数是否有逐项证据，而不是只有总体印象。
- 环境差异是否解释了结果差异，例如模型、工具或上下文长度变化。
- 报告是否把一次独立 replay 与外部采用、用户数量或项目影响力区分开。

维护者可以接受、要求补充，或将结果标记为不可比较。不可比较的报告仍可作为失败模式线索，但不应进入版本对比或 OSS 申请中的成功证据。

## 结果解释边界

- 一次独立 replay 证明的是“在记录环境下完成了一次可复核运行”。
- 多次来自不同环境的 replay 可以帮助发现稳定失败模式或环境敏感性。
- replay 数量不等于外部用户数量，也不等于生产可靠性。
- 没有原始输入、commit 和评分证据的截图或摘要，不作为完整 replay 证据。
